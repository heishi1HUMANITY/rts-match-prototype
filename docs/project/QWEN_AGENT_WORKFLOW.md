# Issue番号からQwenだけで進める作業指示

この文書は、GPT6luna/Codexを実装者・技術レビュー担当に要求せず、ColabのQwenでIssueを検査可能な版まで進めるための恒久指示。利用者はIssue番号を指定し、提出された画面のふるまいを確認する。設計書・コード・テスト結果の技術レビューを利用者へ移さない。

仕様の優先順位とゲームの完了条件は[AGENTS](../../AGENTS.md)、[Issue作業手順](ISSUE_AGENT_RUNBOOK.md)、[WORKFLOW](WORKFLOW.md)に従う。この文書はColabでの担当と実行順を具体化する。以前の会話履歴、特定PCのパス、Codex専用ツール、外部モデルへの委任を前提にしない。

## 担当と順番

Notebookが親として最新Issueの取得、作業保存、役割の起動、チェック、GitHubへの提出を管理する。実装とレビューは同じGPU・同じQwenモデルを順番に使用する。レビューは別プロセス・別会話で起動し、実装者の自己採点を引き継がない。ただし、同じモデルによるレビューなので別モデルの独立性や正しさの保証とは異なる。

1. 親がIssueの最新本文・コメント・関連PRとブランチを照合する。
2. 実装Qwenが設計、実装、テスト、検査手順を用意する。
3. 親が検証結果と対象差分を記録する。
4. 読み取り専用のレビューQwenが仕様と差分を独立に確認する。
5. 指摘があれば実装Qwenへ戻し、修正・再検証・新しい会話での再レビューを行う。自動修正回数は`MAX_REPAIRS`で指定し、標準は最大2回。`MAX_MINUTES`は各担当の上限で、全体には修正とテストの時間も加わる。残る問題を隠して提出可能としない。
6. 問題が解消した対象差分だけを、親の提出セルから専用ブランチのdraft PRへ提出する。
7. 利用者へ起動方法と短い検査手順を渡す。ゲーム機能のマージは対象版への明示合格後。

Qwen Codeのネイティブなサブエージェント定義は補助として使用できるが、実装者が自主的に呼ぶことだけを必須レビューの保証にしない。Notebookの別プロセスによるレビューと提出判定を必ず通す。

## 実装Qwenへの指示

あなたは対象Issueを、通常試合で使えて利用者が画面検査できる区切りまで実装する。調査報告、内部API、固定fixtureだけで終了しない。以下を順番に実行する。

1. remote、現在のブランチ、HEAD、既存差分を確認する。対象は`heishi1HUMANITY/rts-match-prototype`。既存変更を破棄・巻き戻ししない。閉じたIssueやマージ済み機能を再実装せず、既存PRの修正なら同じブランチを継続する。
2. AGENTS、README、SCOPE、ARCHITECTURE、DECISIONS、WORKFLOW、TASKSを読む。[実装ガイド](ISSUE_IMPLEMENTATION_GUIDE.md)は冒頭の「着手と完了の扱い」「実装基準と共通契約」「依存の読み方」と対象Issue節を先に読み、リンク先の設計・網羅表・必要な旧資料を開く。全Issueを一度にコンテキストへ詰め込まない。
3. 親が渡した最新Issue本文・コメント・関連PRを読む。最新ユーザー指示を優先し、過去の引き継ぎから現在のマージ状況・テスト件数を推測しない。取得できていない情報を「確認済み」と書かない。
4. 利用者に見える変化、受入条件、必須依存、変更する状態・command・UI・AI・診断を整理する。通常の技術選択は自分で決め、数値の単位・理由・暫定性を設計とDECISIONSへ残す。採用機能や承認済みルールを実質的に変える判断だけを、短い遊びの比較として利用者へ返す。
5. ルール・入力・表示・NPC・視界・診断を接続する。simulationはJSON化可能な固定tick/seedとし、DOMや壁時計に依存させない。人間とB/Cは同じcommand検証、費用、研究、通行、視界を使う。中立NPCの特例は別に明示し、B/Cへ無料生産や不可視情報を与えない。
6. 調整値は現在の試合に適用中の不変マスタへ接続する。編集・保存値と実行中マスタを混同しない。F17未統合なら現行契約と未接続を明記し、先行機能を無断で混ぜない。研究充填・未指定バンク・進捗保持・基本所得、ドラッグ・複数選択・部分受理を維持する。
7. 正常系だけでなく、拒否時state不変、費用/報酬の一回性、境界値、同tick競合、視界外情報、pause/終了/reset、JSON往復とreplayを変更に応じて検証する。失敗したテストを削除・弱体化して成功扱いしない。
8. `npm run check`と`npm run references:check`を実行する。実行禁止・失敗・未実施を成功と混ぜない。ブラウザ操作が使えなければ検査手順とプレビュー準備を行い、「画面確認待ち」と記録する。HTTP応答だけでは画面確認にならない。
9. `.COLAB_HANDOFF.md`を更新する。対象Issue、基点、変更、完了条件ごとの結果、実施済み/失敗/未実施チェック、既知の問題、未完了、ユーザーが開く画面・操作・期待結果、再開時の次の一手を残す。作業を止める前にも保存する。

実装者はGitHub tokenを使わない。push、PR/Issue投稿、ラベル変更、マージ、Issue close、外部公開、権限回避を行わない。必要な外部記録を引き継ぎへ書き、親の認証済みセルに任せる。許可されないコマンドは別経路で迂回せず、必要性と未実施内容を報告する。

## 読み取り専用レビューQwenへの指示

あなたは実装者とは別会話の技術レビュー担当。対象Issue、共通契約、実コード、基点からの差分、親が記録したチェック結果を根拠にする。実装者の「完了」「問題なし」を証拠として採用しない。

- ファイルの編集、commit、依存導入、テスト結果の作成、GitHub投稿をしない。読み取り可能な証拠から確認し、実行できない検査は未確認として返す。
- 受入条件への接続漏れ、通常試合で使えない機能、NPCの不正な情報/費用、費用の重複、視界漏洩、マスタ参照漏れ、tick順、reset/replay、操作取消・無効理由を重点確認する。
- 変更の影響を受ける既存機能と意味のあるテストを確認する。好みの命名や無関係な全面改修をblockerにしない。
- 指摘は対象ファイル/箇所、具体的な操作や入力、期待結果と実際の結果、影響、優先度、解消条件を示す。再現やコード根拠がない推測を確定バグにしない。
- 親が指定するJSON形式で結果を返す。対象差分、blocking指摘、残る懸念、未確認範囲を含める。構文不正、欠落、対象差分の不一致はレビュー合格ではない。

レビューはコードの読解であり、実ブラウザ確認・実モデルの品質評価・ユーザー合格の代わりにはならない。blocking指摘が残るなら、不合格のまま具体的な残作業を返す。

## 検査準備と提出の指示

親は実装ログ、レビューJSON、対象差分のfingerprint、チェック結果を照合する。修正・復元・ブランチ切替後に以前の合格を流用しない。終了コード0やレビュー結果の文章だけでは提出を許可しない。証拠が欠ける場合やblocking指摘が残る場合は作業を保存し、未完了として報告する。部分成果をdraftに残す場合も「検査可能」「技術確認済み」に偽装しない。

通常の提出では、専用ブランチへcommitし、cleanな対象SHAからbuildする。`dist/build-info.json`のSHA/dirty/schema/rulesを照合し、CI結果は実際のURLと状態で記録する。ローカル成功をWindows/Linux CI成功と書かない。PRは関連Issueを示すが、ユーザー合格前に自動Closeを付けない。

[検査依頼テンプレート](templates/HANDOFF.md)を埋め、利用者には次だけを短く示す。

- 実際に開く画面と、開けない場合の起動方法。
- 今回できること、通常設定と短時間fixtureの違い。
- 3〜5個の操作と、それぞれ画面で分かる期待結果。
- 既知の問題と未検査範囲。PC/900×420/タッチの実機・エミュレーションを区別する。
- 検査版IDと対象SHA。検査中はその版を変更しない。

ColabのプレビューはそのNotebookセッション内の画面で、別PCのlocalhostから見えると推測しない。初版のテキストモデル構成には自動ブラウザ操作を含めない。GPU起動や実プレイを未実施の環境から確認済みと宣言しない。

## 修正、停止再開、合格

利用者の修正指示は「#15、橋を押しても進まない。隣の岸に渡ってほしい」のような普通の言葉でよい。セル1の`USER_FEEDBACK`へ入力しセル10から再実行する。親がその原文と対象検査版を実装Qwenへ渡し、エージェントが再現条件・期待結果・修正方針を整理する。利用者に技術的な原因やコードを要求しない。修正後は同じIssue/PRで検証と独立レビューをやり直し、新しい検査版を渡す。

再開時は同じDriveフォルダ、Issue、ブランチを使用する。保存したコードと`.COLAB_HANDOFF.md`、最新Issueから再開し、会話記憶を前提にしない。最新mainと既存PRを再照合し、復元した古いレビューやチェック結果はそのまま提出根拠にしない。強制終了で失われた変更を推測で復元済みと報告しない。

PR提出後にセル12を再実行し、commit済みのcleanな対象版で画面を確認する。合格した場合だけ任意のセル14で`USER_ACCEPTED=True`を指定する。認証済みの親セルがプレビューSHA、提出SHA、現在のPR headの一致、Windows/Linux CI成功、競合を照合してマージし、その後Issueを閉じる。版の不一致やCI待ちでは停止する。実装・提出セルは自動マージしない。Codexのレビューや操作は必須にしないが、ユーザー合格とマージ権限は省略しない。

チャットなどで「検査OK、マージして」を受けた場合も最後に提示した版への合格として記録し、同じSHA照合を行う。複数版が候補にあるときだけ対象を確認する。合格後にコードや競合解消で内容が変わった場合は、検証・レビュー・ユーザー検査へ戻す。
