# Issue番号から進める実装ガイド

ユーザーが「#15を進めて」のように番号だけを指定した場合の実装入口。対象Issueの最新本文・コメントと最新のユーザー指示を読み、この文書の対応節から、設計判断、実装、検証、画面検査への引き渡しまで進める。これは未実装機能の作業計画であり、ここに書いた型・command案が既に存在するという意味ではない。

## 着手と完了の扱い

1. `AGENTS.md`、`README.md`、[SCOPE](SCOPE.md)、[ARCHITECTURE](ARCHITECTURE.md)、[DECISIONS](DECISIONS.md)、[WORKFLOW](WORKFLOW.md)、[TASKS](TASKS.md)、対象Issueを読む。作業差分を確認し、ユーザーの変更を保全する。
2. 対象Issueに必要な前提がmainへ合格・マージ済みか確認する。未充足なら、公開契約の設計・検査計画までは進め、必要な先行Issueと理由を報告する。番号一つの依頼を、未依頼の別Issueの本実装やマージ許可へ広げない。すでに一連の実装が依頼されていれば、その範囲で前提から進める。
3. `docs/project/preparation/Fxx_DESIGN.md`などに、データ、command検証、tick内の順序、視界、NPC、UI、検査シナリオを具体化してから実装する。通常の技術選択・データ構造・暫定調整値はエージェントが決め、理由と暫定性を記録する。ユーザーに設計書やコードの技術レビューを要求しない。
4. 採用/除外、通常試合の長さ、再建・脱落条件など、ユーザー体験や依頼範囲を実質的に変える判断だけは、比較できるふるまい案を示して方針を確認する。それ以外の内部タスクごとの承認待ちは作らない。
5. ルール・UI・B/C・視界・診断を一つの動く区切りとして揃える。`npm run check`と`npm run references:check`、関係する実ブラウザ操作、900×420/PCの確認を行う。環境制約で未検査ならそのまま記録し、制限を回避したり、合格と推測したりしない。
6. 通常設定と短時間fixtureを用意し、起動手順、対象commit、ユーザーがする短い操作、期待する画面のふるまいを渡す。[WORKFLOW](WORKFLOW.md)どおり、明示合格後に対象内容をマージする。CI成功やこの文書の作成は合格ではない。

## 実装基準と共通契約

2026-10-12にこのガイドを作成したmain相当のソースは、G3＋F01、`schema5 / rules g3-v1`。F02は別作業で検査中だった。**着手時には実際のマージ状態を再確認する**。F02合格版なら`marchOrder`、`march`、`simulation/march.ts`、`ui/march-target.ts`と`schema6 / rules f02-v1`が加わる。版番号をこの記述から固定せず、`simulation/config.ts`、`types.ts`、`runtime/diagnostics.ts`、ビルド情報を照合する。

現存する接続先は次のとおり。以下の各節で「追加案」とする名前は新設候補で、既存APIではない。

| 責務                      | 現存するファイル                                                                                                           |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| 状態・初期化・数値        | `src/simulation/types.ts`、`match.ts`、`config.ts`、`random.ts`                                                            |
| 共通command・進行         | `src/simulation/commands.ts`、`step.ts`                                                                                    |
| 地形・経路                | `src/simulation/map.ts`、`pathfinding.ts`                                                                                  |
| 交戦・制圧・経済          | `src/simulation/combat.ts`、`capture.ts`、`economy.ts`、`production.ts`、`research.ts`、`tickets.ts`、`outcome.ts`         |
| 情報境界                  | `src/simulation/visibility.ts`、`view.ts`                                                                                  |
| 人間命令・NPC再生成・診断 | `src/runtime/controller.ts`、`advance.ts`、`diagnostics.ts`、`src/ai/strategy.ts`                                          |
| 操作・表示                | `src/main.ts`、`src/ui/input.ts`、`hud.ts`、`styles.css`、`src/render/board.ts`、`view-model.ts`、`src/assets/manifest.ts` |

- simulationはJSON化可能、整数tick・固定小数で決定的にする。追加の予約、建築、効果期限、乱数状態、ID採番も状態へ保存し、壁時計やDOMへ隠さない。新しい状態/ルールに対してschema/rulesと旧診断の扱いを更新する。
- 現行tickは移動→同時交戦→制圧→経済→研究充填→生産→チケット→脱落/決着→視界更新。F02があれば移動前に追跡更新、交戦後に目撃撃破の解除が入る。新段階の挿入位置、当tickか次tickから効くかを設計へ追記する。全攻撃のダメージは同じ元snapshotから集計する。
- 人間とB/Cは同じcommand、費用、研究、通行、視界を使う。NPC判断は`FactionView`だけを入力とし、`runtime/advance.ts`を診断でも使う。人間履歴と自動再生成するNPC命令を二重適用しない。中立守備・現地勢力のルールは別に明示し、B/Cを無料生産へ変えない。
- 地形・拠点予定位置など公開情報と、現在可視/古い記憶/未観測の動的情報を分ける。敵の資源・研究・キュー・命令・視界外の位置を通常UI/render/AIへ渡さない。新しい施設・効果・予測にも同じ境界を設ける。全情報診断は明示された開発経路だけに置く。
- 自軍ドラッグ、地面パン、複数選択、一括の部分受理、停止、HUD/盤外/二本指/Escの取消を維持する。新しい対象をpickへ足す場合はpreviewとdropで同じ解決規則を使い、操作一回でcommandが重複しないようにする。
- 研究は選択中へ既存バンク＋所得を充填、必要量で即完了、余りバンク。未指定は全バンク、切替/解除でも研究別進捗保持、返金なし。基本0.2pt/秒を維持する。固定研究時間・予約列・開始時一括課金を復活させない。
- 調整値は[F17設計](preparation/F17_DESIGN.md)の試合ごとの不変マスタへ接続する。以下の旧値は参考で、無断で採用済みにしない。新しい機能のテスト用値と通常値を区別する。
- 各ルールIssueで、拒否時の入力state不変、支払い/報酬の一回性、pause/終了時停止、reset時の予約・効果・選択消去、JSON往復と同履歴replayを確認する。これらに加えて各節の固有境界をテストする。

## 依存の読み方

「必須」は対象を動く機能として完成するための前提。「契約先行」は型・意味・更新通知を共同設計すればよく、そのIssue全体の合格を待つ依存ではない。「後続統合」は機能が存在した時点で接続する責務であり、未接続を残して全体完成とはしない。

## #16 / F04 橋・索道の建設・奪取・解体

参照: 機能仕様書4.2、計算モデル9章。必須: F03の予定地/通行照会、F17。契約先行: F09の該当解放研究、F08の索道不可兵種。後続統合: F11アンカー、F12補給線。全研究/全施設を待たず、必要な研究定義と実効果を同じ区切りで接続する。

- 追加案: 渡河状態にID、両端cell、kind/等級、owner、HP、建設/解体job、進捗、最終被弾tickを持つ。`build-crossing`/`dismantle-crossing`等のcommand案を`commands.ts`へ追加し、所有・隣接した有効陸上部隊・研究・費用・重複開始を原子的に検証する。
- 建設は有効な建設部隊が隣接中だけ進む。離脱/撃破で進捗保持・停止、再接近で再開。先行建設権、複数部隊の加速有無、建設中HPと攻撃可否、敵による中断を設計する。奪取/破壊/解体の同tick優先順を一か所で確定する。
- 所有軍だけ通行、索道の兵種制限、奪取/解体でroute再評価。辺上の部隊を消したり敵岸へ瞬間移動させたりしないため、閉鎖時の半セル処理を明文化する。F02追跡と後の補給線にも同じ変更契機を渡す。
- render/UIに予定地pick、費用・研究不足・隣接不足、進捗、停止理由、解体確認操作を追加。敵の建設/HP更新は可視時のみ。B/Cは同じ費用で建設し、自軍が通れる経路を選ぶ。
- 検証: 重複開始で一回課金、離脱/再開、同tick奪取と解体、破壊時の半セル、通行権変更後の既存route、索道不可兵種、不可視敵の建築進捗で自軍previewが変わらないこと。
- ユーザー検査: 隣接→建設→離れると停止→戻って完成→通行→奪取/解体で経路変更を短時間設定と通常試合で試せる。

未決/提案: 閉鎖時は進行中の一辺の完了先を固定し、その後停止/再経路化する案を安全な初期案とする。旧橋I〜III/索道I〜IIの費用と60〜90秒を自動採用せず、F16時間予算内で調整する。取消/奪取時の返金率も支払い済み額と共に定義する。

## #17 / F05 中立守備と制圧

参照: 機能仕様書3.4/3.6、計算モデル6/7/26章。必須: F03拠点規模、F17、F08の攻撃領域/制圧可否契約。既存2陸上兵種で縦に実装し、後から航空/水上を接続できる形にする。

- 守備を対戦FactionIdへ足さず、拠点に紐づく守備状態としてID・HP/maxHP・攻撃定義・復活条件を追加する。`combat.ts`に守備との同時交戦、`capture.ts`に守備生存→拠点HP→所有変更の段階を接続する。
- G2の無人30tick制圧とHP0制圧の併用/置換を明示する。競合陣営が同tickにHP0へした場合の所有候補、陸上不在なら所有不変、制圧後HPと守備復活条件を決める。ダメージと報酬は陣営ID順で有利にならない方法を使う。
- viewには可視守備のHP/状態のみ、記憶には観測値と時点のみ。B/Cも守備を倒す必要があり、守備が残る拠点から収入/補給・ticketを得ない。守備撃破/制圧報酬があるなら研究バンク/充填へ正規接続する。
- 拠点ポップに守備HPと拠点HPを別表示し、未観測では数値を断言しない。rendererの守備表示・交戦表示とpickを追加する。
- 検証: 守備生存中に拠点へダメージが抜けない、同時撃破、航空/水上だけで所有変更しない、競合制圧、報酬の一回性、中立化時の復活、守備が視界外で傷ついても記憶不変。
- ユーザー検査: 守備を削る→倒す→拠点HPを削る→陸上部隊で制圧→所得増加が説明どおり見える。
- `defenses.respawnEnabled`をマスタから切替できるようにする。既定は有効。無効時は開始時の守備だけを配置し、撃破後の時間復活も所有拠点の破壊/中立化に伴う守備再配置も行わない。保存後は新規試合から適用する。

未決/提案: 制圧競合は有効陸上陣営が一つのとき確定、複数なら中立HP0で競合保留とする案を検討。旧守備HP/火力や制圧後30%回復はF17の暫定値として比較し、G2からの変更を検査へ示す。

## #18 / F06 現地勢力

参照: 機能仕様書3.8、計算モデル13章。必須: F03、F05、F17と必要兵種のF08契約。契約先行: F16の出現時刻/通常時間、F07の徘徊統合方針。F16全体完成を待たない。

- `FactionId = A|B|C`の順位参加者と独立した勢力/所有者型を設計する。基地owner、攻撃敵対判定、制圧候補、viewの所属表示を監査する。`factions`へ単純に第4軍を追加すると順位・ticket平均・人間操作権が壊れるため避ける。
- 追加案: 本拠状態、spawn予定tick、roster index、成長係数、部隊上限、初期所有地、壊滅フラグを保存する。専用の純粋方針/更新モジュールを追加し、`step.ts`へ生産・救援・守備・侵攻を接続する。旧本拠HP6000/2500、初出現2分/4分の矛盾を比較する。
- 討伐/奪還報酬は原因イベント一回に限り、研究は現行充填ルールへ入れる。本拠壊滅後は生産停止、部隊除去/所有地中立化/守備復活を同tickで処理し、除去部隊へ重複討伐報酬を出さない。
- 公開概況の項目を明示的に限定し、可視の所属・位置・HPだけ通常viewへ出す。旧「視界なし/地形無視/無料定期生産」は現地勢力固有の候補であり、B/Cへ流用しない。採用する特例は画面で説明する。

未決/提案: 最初は対戦軍と同じ通行・観測基盤を使い、特例は必要性が確認できたものだけ設計に追加する。世界観や対戦順位参加者を増やさない。本拠/侵攻の存在自体を省く代替にはユーザーの方針確認が必要。

## #19 / F07 徘徊の採否と定期圧力

参照: 機能仕様書3.1/3.4/4.1、計算モデル13章の「徘徊廃止・現地勢力へ統合」。必須: F06とF16の時間設計、F17。設計比較はこれらの実装前から進める。

## #5 / G4 初見UIと全体通し検査

参照: [TASKSのG4](TASKS.md#g4--m4-初見で遊べるuiと導入)、[REFERENCES](REFERENCES.md)のS05/S05a〜d/S06、機能仕様書2.4/2.5/6章。必須: G3合格版。各UIの作業は対象機能と並行可能だが、最終合格は#12の全採用機能・F16統合後。

- `ui/hud.ts`/`styles.css`を中心に、ミニマップ、可視敵詳細、建築/強化/渡河ポップ、研究ツリー、生産/部隊/態勢、戦況、結果詳報を揃える。各ルールIssueで作った操作を移設/整理し、G4まで必要UIを欠いたまま待たせない。

G4は新たなネット/文明/課金/試合外画面を作る依頼ではない。全機能の未決定や未実装をUI仕上げで覆わず、#12と対応Issueへ戻して解消する。
