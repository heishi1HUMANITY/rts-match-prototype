## G1 / M1: 盤面で部隊を動かせる

ブランチ例: gate/g1-map-movement。前提: M0。主な編集範囲: src/simulation、src/render、src/ui、src/main.ts、必要な設定・テスト・docs/project。

実装前の具体設計は [G1_IMPLEMENTATION_DESIGN.md](G1_IMPLEMENTATION_DESIGN.md)、lunaへの段階別指示は [G1_LUNA_INSTRUCTIONS.md](G1_LUNA_INSTRUCTIONS.md) を参照。設計準備は実装完了を意味しない。

| ID   | 実装内容                                    | 依存           | 技術的な完了条件                                                                                 |
| ---- | ------------------------------------------- | -------------- | ------------------------------------------------------------------------------------------------ |
| T101 | 最小盤面・進行ルールとAPIを定義             | M0             | 盤面寸法、初期配置、tick、経路、停止/非表示復帰、seedの扱いをDECISIONSへ記録。旧数値の採否を明示 |
| T102 | seed付きマップと3陣営の初期配置             | T101           | 同一seedで同一地形・配置、陣営間の状態独立性、配置が通行可能であることをテスト                   |
| T103 | 共通command、固定tick、選択対象の検証、移動 | T102           | 他陣営操作・不正入力拒否、同じseed/命令列の再現、到達不能/境界/停止復帰をテスト                  |
| T104 | Three.js盤面とカメラの描画アダプター        | T102の状態契約 | 斜め見下ろし、パン/ズーム、陣営色＋記号、resizeとdispose。ルールをrendererへ置かない             |
| T105 | 入力・開始・リセット・検査シナリオの統合    | T103,T104      | マウス/タッチ、自軍選択、移動先表示、HUDの入力分離。リセットで状態/入力/タイマーを初期化         |

T103とT104は型・境界が決まった後だけ並列化できる。通行可能な簡易地形に限定する場合はT101で明示する。

ユーザー検査:

- G1-01: 検査用seedで開始し、自軍を選択して指定した場所へ移動できる。
- G1-02: 敵軍を選んでも命令できず、到達不能な指示には理由が見える。
- G1-03: パン/ズームとHUD操作が誤った移動命令を発生させない。
- G1-04: 停止/再開、タブ非表示からの復帰、リセット後も正常に操作できる。
- G1-05: 900×420とPCで盤面と操作UIが重ならない。実機/エミュレーションの確認範囲を明記する。

## G2 / M2: 戦略ループを手動で試せる

ブランチ例: gate/g2-strategy-loop。前提: G1合格・マージ。主な編集範囲: src/simulation、src/render、src/ui、検査シナリオ・テスト・docs/project。

G1検査待ちの先行準備は [G2設計案](preparation/G2_DESIGN.md)、[段階別指示案](preparation/G2_AGENT_INSTRUCTIONS.md)、[テスト行列案](preparation/G2_TEST_MATRIX.md) を参照。これは調査・設計であり、G2の実装着手・暫定値の採用・タスク完了を意味しない。実装前にG1合格版との差分を照合する。

| ID   | 実装内容                                | 依存       | 技術的な完了条件                                                                                 |
| ---- | --------------------------------------- | ---------- | ------------------------------------------------------------------------------------------------ |
| T201 | 視界と陣営別の可視情報                  | G1         | 視界外の敵状態をUI/将来AIへ渡さない。初期探索、視界更新、境界のルールを記録・テスト              |
| T202 | 補給、拠点収入、生産キュー、最小兵種    | G1         | コスト/所要時間/上限を定義し、資源不足、二重入力、キャンセルの挙動をテスト                       |
| T203 | 自動交戦、HP、拠点制圧、首都の最小扱い  | T201,T202  | 射程、交戦対象、所有変更の順序を定義。同時交戦・制圧競合・破壊済み対象をテスト                   |
| T204 | 最小研究、チケット更新と決着への契約    | T202,T203  | 試合内だけの研究。充填/切替/進捗保持/条件判定とチケット変動をテスト。首都/脱落との関係を暫定決定 |
| T205 | 生産/研究/拠点HUDと固定敵の検査シナリオ | T201〜T204 | mockのS05/a/b/c/dを参照した操作UI。NPCなしで一連の変化を再現。未実装AIと検査用設定を明示         |

研究の枝・兵種数は最小構成を判断記録へ残す。全6兵種・全4分岐を暗黙に必須としない。
中立守備の有無も決定する。視界ルールはG3へ先送りしない。

ユーザー検査:

- G2-01: 拠点を制圧すると所有表示と収入が変わり、生産に利用できる。
- G2-02: 生産を連続操作しても無料/二重生産が発生せず、資源不足の理由が分かる。
- G2-03: 固定敵との交戦でHP・撃破・制圧が表示と一致する。
- G2-04: 研究対象へポイントを充填して、完了後の効果とチケット変化を確認できる。
- G2-05: 視界外情報が漏れず、パネルを開閉しても盤面を操作できる。研究中の試合進行が分かる。

## G3 / M3: NPC2陣営との試合が最後まで成立する

具体契約は [G3_DESIGN.md](preparation/G3_DESIGN.md)、画面検査手順は [G3_SCENARIOS.md](inspection/G3_SCENARIOS.md) を参照。

ブランチ例: gate/g3-npc-match。前提: G2合格・マージ。主な編集範囲: src/ai、src/simulation、src/ui、src/render、テスト・docs/project。

| ID   | 実装内容                           | 依存       | 技術的な完了条件                                                                                  |
| ---- | ---------------------------------- | ---------- | ------------------------------------------------------------------------------------------------- |
| T301 | 2陣営のNPC意思決定                 | G2         | 生産・移動・制圧・交戦/研究の判断を可視情報と共通commandで行う。無料行動/全知情報がないことを検証 |
| T302 | 勝敗、脱落、時間切れ、同点順位     | G2         | チケット/首都/再建の採否、時間上限、タイブレークを確定。各終了条件、同時脱落、終了後入力をテスト  |
| T303 | 開始→結果→再戦と試合ライフサイクル | T302       | 結果理由/順位を表示し、再戦で状態、資源、研究、AI、タイマー、入力、描画資源を初期化               |
| T304 | 三つ巴の通し検証と短時間シナリオ   | T301〜T303 | 複数seedでNPC停止や不正状態を検出。短時間と通常設定を区別し、終了条件別の再現手順を用意           |

T301とT302はG2の状態契約が安定していれば並列化できる。合格にはNPCが動くだけでなく終了・再戦まで必要。

ユーザー検査:

- G3-01: プレイヤーとNPC2陣営がそれぞれ生産・進軍・交戦する。
- G3-02: 決定した脱落条件と時間切れの両方を、検査シナリオで確認する。
- G3-03: 勝敗理由/順位/同点時の処理が説明と一致し、終了後に命令できない。
- G3-04: 再戦で前の試合の部隊・資源・研究・入力が残らない。
- G3-05: 検査用短時間設定に加えて、通常設定でも一試合が進む。

## G4 / M4: 初見で遊べるUIと導入

ブランチ例: gate/g4-first-play。前提: G3合格・マージ。主な編集範囲: src/ui、src/render、必要なsimulation修正・テスト・docs/project。原本mockは編集しない。

| ID   | 実装内容                               | 依存       | 技術的な完了条件                                                                                |
| ---- | -------------------------------------- | ---------- | ----------------------------------------------------------------------------------------------- |
| T401 | mockに沿ったHUD/研究/生産/結果の仕上げ | G3         | S05/a/b/c/dとS06の配置・面・階層を比較。世界観要素を除く差分理由、色＋記号、選択/無効理由を記録 |
| T402 | 開始導線、短い操作ガイド、再表示       | G3         | 初見の操作順を機能名で案内。スキップ/再表示、マウス/タッチの説明が実装と一致                    |
| T403 | 横持ち/PC、入力と描画の復帰、性能確認  | T401,T402  | 900×420とPC、resize、停止/復帰、WebGL失敗時の案内を確認。対象端末と実測条件を記録               |
| T404 | 初見通しプレイと検査指摘の収束         | T401〜T403 | 通常設定で開始→制圧→生産→研究→交戦→結果→再戦。未検査/既知の制約を明記                           |

ユーザー検査:

- G4-01: 説明役なしで開始し、ガイドを使って制圧・生産・研究・交戦ができる。
- G4-02: 900×420とPCで文字とボタンが読め、必要な盤面がパネルに隠れない。
- G4-03: 色だけに頼らず3陣営・選択対象・操作できない理由を理解できる。
- G4-04: 通常設定で結果から再戦でき、画面サイズ変更やガイド再表示でも操作が崩れない。
- G4-05: 原本mockとの見た目の差分と、初期対象外の要素を区別して判断できる。

## 共通の技術検証

各Gでnpm run check、npm run references:check、Windows/Linux CI、実ブラウザ操作を実施する。
ルール変更には意味のある再現テストを追加し、900×420とPCの結果と検査対象commitを残す。
過去の試験結果を未検証の新しい版へ流用しない。
