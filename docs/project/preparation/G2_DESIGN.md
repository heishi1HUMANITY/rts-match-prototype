# G2 戦略ループの先行設計案

2026-10-11。Issue #3のT201〜T205の実装契約。G1検査待ち中に先行設計し、G1合格・マージ後のユーザー指示で実装へ採用した。数値はG2の検査用の暫定バランスであり、完成版のバランス確定ではない。

先行設計のG1観測commitは `2a1843e751a39e61480a472d283d47c183b6b310`。合格版 `411c8becc30dc978ff6e6db244eaf6632218e29f`、mainマージ `eeaf2638f45ecb634b079bf4e2f3a0e02fade1ba` と照合し、simulationの差分なしを確認。新しい部隊ドラッグ&ドロップを維持する。G2は `gate/g2-strategy-loop` で実装し、起動中のG1検査distはG2の検査準備まで維持する。

## 1. 到達点と対象外

人間が制圧→収入→生産→固定敵との交戦→研究→チケット変化を試せる。NPCは同じルールで被弾・維持費・資源・視界を処理するが、自発的な命令生成はまだ行わない。

G2では視界・地形を全陣営で共通に制約する。勝敗・脱落・再建・AI・結果画面はG3へ残す。文明、永続研究、河川、渡河点、補給線ネットワーク、中立守備NPC、防御施設、部隊の態勢、指導者窓は追加しない。「補給」は資源と維持費を指し、補給線を実装したとは表示しない。

## 3. 状態と公開API案

状態schemaを4、rulesVersionを `g2-v2` に更新する。v1/v2/v3診断の互換読込みは提供せず、リプレイは同一schema/rulesVersionを必須とする。G1診断ファイルをG2として解釈しない。

- `FactionState`: id/controller、supplyCenti、researchCenti、ticketsCenti、productionJobs、activeResearch、researchProgressCenti、completedResearchIds、nextUnitSerial、nextJobSerial。
- `UnitState`: G1のid/factionId/cell/path/edgeProgressにkind、hp、maxHpを追加。初期01=強襲、02=偵察。IDは陣営内の単調増加番号で、撃破・取消後に再利用しない。
- `BaseState`: id、kind(`hq`/`outpost`)、cell、owner(`FactionId`/null)、hp、maxHp、captureCandidate、captureTicks。首都の元陣営は変更不可のフィールドで保持。
- `FactionKnowledge`: visible/exploredの行優先1600要素と、拠点のlastSeen情報（owner、hp、seenTick）。未観測と観測済みを区別する。
- `MatchState`: 上記に加え、scenarioIdとG1のseed/map/phase/elapsedTicksを保持。すべてJSON化可能。DOM・Three.js・時刻APIを含めない。
- `createMatch(seed, { scenarioId })`、`applyCommand(state, actor, unknown)`、`stepMatch(state)`、`getFactionView(state, actor)`を公開する。scenarioIdは列挙済みIDのみ。未指定は通常設定。

`applyCommand`の戻り値はG1同様の `CommandResult = { ok:true, state } | { ok:false, state, reason }`。runtimeは受信順に同期適用し、tickBeforeとseqを履歴へ記録する。tick処理中に命令を割り込ませず、開始直前に受理した命令は次のstepへ、step完了後に受理した命令はその次へ反映する。同一tickの取消と新規予約もseq順で適用し、種類別の優先順は設けない。リプレイも同じ順序を使う。

追加命令:

| 命令               | 必須payload       | 受理時の効果                                   |
| ------------------ | ----------------- | ---------------------------------------------- |
| enqueue-production | baseId, unitKind  | 補給を即支払い、IDと部隊枠を予約               |
| cancel-production  | jobId             | 支払済み補給を全額返し、その予約を除去         |
| start-research     | researchId / null | 研究対象を選択してバンクを充填。nullで指定解除 |

move/stop/start/pause/resumeはG1の形を維持する。追加キー、不明ID、NaN/小数/不正actor/phaseを拒否し、失敗時は元state参照を返す。actorはUIから自由入力させない。将来AIも同じapplyCommandを通す。

追加拒否コードは `BASE_NOT_FOUND`、`JOB_NOT_FOUND`、`INVALID_UNIT_KIND`、`RESEARCH_NOT_FOUND`、`HQ_UNAVAILABLE`、`INSUFFICIENT_SUPPLY`、`UNIT_LIMIT`、`QUEUE_FULL`、`ALREADY_RESEARCHED`、`PREREQUISITE_MISSING`。共通形式/actor/phase→観測可能な対象存在→所有→利用可能性→枠・研究条件→資源の順で検証する。非可視の敵部隊IDと存在しないIDはどちらもUNIT_NOT_FOUND、他陣営のjobIdと存在しないjobIdはどちらもJOB_NOT_FOUNDとする。可視の敵部隊はNOT_OWNER。隠れた対象の存在確認を拒否理由の違いから探らせない。拠点ID/種類は公開、自己所有の喪失は自軍報告で既知だが、他陣営同士の所有変更は拒否理由に含めない。

## 4. 配置と計算値

G1合格版の初期部隊位置を維持する前提案。首都はA(6,34)、B(33,34)、C(20,5)。拠点は(20,12)、(20,20)、(20,28)。首都はG1のspawn保護範囲、拠点は中央通路上にあり、新しい乱数消費は不要。合格版に保護範囲の変更があれば再確認する。地形と拠点は公開の図面情報、所有/HPは可視情報とする。

資源・チケットは1単位=100の整数で保持し、画面は切り捨てた整数を表示。rateは毎tickの整数値とし、浮動小数の蓄積を使わない。

設定値も内部APIではCentiを接尾辞とする（初期補給20000、強襲費用12000、偵察費用6000、研究I費用6000、研究II費用9000、初期チケット100000、撃破損失800、首都損失10000）。下表の生産補給/損失チケットは画面単位、維持費欄だけCenti/tick。表示時以外に100倍/100分の1の変換を挟まない。

| 値                 | 強襲        | 偵察      |
| ------------------ | ----------- | --------- |
| 生産補給           | 120         | 60        |
| 生産tick           | 120（12秒） | 60（6秒） |
| 最大HP             | 100         | 60        |
| 基本ダメージ/tick  | 2           | 1         |
| 射程セル           | 2           | 1         |
| 視界セル           | 6           | 8         |
| 維持費Centi/tick   | 5           | 3         |
| 撃破時損失チケット | 8           | 8         |

首都HP300/視界6/補給Centi毎tick40、所有拠点HP100/視界4/補給20/研究10。中立拠点HP0。地形障害物は視界・射撃を遮らない（遮蔽はG2対象外）。移動・射撃中も制圧可能。

距離は2倍整数座標を使う。セル中心は(2x+1,2y+1)、移動途中はそこへedgeProgress×(次セル−現セル)を加える。次セルがない場合は加算0。これで半セルの中間位置も整数となる。視界・射程・制圧は距離二乗 <= (2×半径)^2で境界を含む。描画のalphaやraycast座標はルールに渡さない。

## 5. 視界・陣営view

生存自軍とHP>0の所有拠点の視界の和がvisible、exploredは過去visibleとのOR。全陣営に対し開始時と各tick末尾で計算する。セル可視maskはセル中心、部隊可視は2倍整数の現在位置で判定するため、半セルが可視境界にあるときはmaskと部隊判定が異なる。霧の描画はセル単位の近似であることをテストと描画仕様に残す。命令受付後の視界キャッシュは次tickまで変わらない。

`getFactionView`は次だけを新しいオブジェクトとして返す:

- 公開: seed、phase、tick、地形、拠点ID/kind/位置、A/B/Cのチケット（公表値）。
- 観測: viewerFactionId、その陣営のvisible/explored各1600要素mask。元stateと参照を共有しない。
- 自軍: 自軍資源・キュー・研究・全部隊のHP/経路/目的地、自軍所有拠点の現在状態。
- 敵: 可視判定を通過した生存部隊のID/factionId/kind/2倍整数位置/HP/maxHPのみ。経路・目的地・キュー・資源・研究・非可視部隊IDは含めない。DTOは列挙したfieldだけを構築し、元UnitStateのspread/Omitで作らない。
- 非可視拠点: `unknown / remembered / visible / owned`で判別する型を使い、未観測のunknownをowner=null（中立）と混同しない。既観測ならlastSeenと観測tickを返し、現在値のように表示しない。自軍が所有を失った拠点は自軍報告として喪失だけ通知し、記憶にselfReportedLost=trueを付ける。新所有者は可視になるまで更新しない。

拠点のvisible/owned DTOにはowner/hp/maxHp/captureCandidate/captureTicksを含め、現在進捗を表示する。rememberedは観測時owner/hp/seenTickだけとし、制圧進捗は保持・表示しない。unknownはこれらの動的項目を持たない。

rendererとHUDの通常入力をFactionViewへ変更する。`MatchState`を渡して各所でfilterする設計は採用しない。敵の線・目的地・非表示DOMラベル・pick・通知にも非可視情報を渡さない。霧は未探索を濃色、探索済み非可視を薄色で覆い、所有拠点は自軍報告として操作できる。

現viewから消えた敵はmesh/DOM/pickから即除去し、前viewの敵を補間表示し続けない。新たに見えた敵も隠れていた過去位置から補間しない。全陣営部隊数・所有数・隠れた撃破者ID・攻撃線・通知を別経路で渡さない。DTOは元stateと可変参照を共有しない。

診断保存だけは全stateを扱う開発用経路として分離し、「全情報を含む診断JSON」と表示する。将来AIにはviewだけを渡す。敵位置だけを変えた2つのstateについて、双方で非可視ならviewが同一であることをテストする。

## 6. 生産・研究・資源

生産は陣営に1列、active1＋待ち2の最大3予約。自軍の稼働首都のみ指定可。予約時に資源と部隊枠を確保し、activeだけremainingTicksを減らす。0で首都セルへ生成し、次の待ちは次tickから進む。重なりを許容するG1ルールを維持し、ランダムなspawnと押し出しは追加しない。生産された部隊は次tickから移動/攻撃/制圧/維持費の対象になる。視界には生成tick末尾から含める。

enqueueは所有/稼働状態→生存＋予約枠→キュー数→資源の順で検証し、すべて通った場合だけ支払い・ID採番・予約を単一の新stateとして確定する。失敗時にカウンタだけ進めない。研究選択は前提/完了済みの検証後に対象を確定し、バンクから必要量だけ充填する。ポイント不足でも選択できる。

取消はactive/待ちのどちらも全額返金。取消を繰り返しても資源が増えず、完了済みIDの取消は拒否。連続enqueueは別の有償注文として扱い、受理した件数だけ資源と枠を確保する。ネットワーク再送用の重複排除IDはG2では追加しない。HUDの1clickは1commandだけ生成する。首都破壊時にはその陣営の全生産予約を全額返金して取消し、同tickの生成を防ぐ。部隊・所有拠点・資源・研究は残る。G2では再建を提供しない。

研究は `firepower-1`（必要60ポイント、攻撃+1HP/tick）、`firepower-2`（必要90ポイント、前提1、さらに+1）。強襲・偵察に同じ加算を適用。追加の固定研究時間はない。1件を選択し、既存バンクと毎tickの収入から未充填分だけを移す。必要量に達した瞬間にcompletedへ追加して選択を解除し、余剰はバンクへ残す。次の研究を自動選択しない。

未指定なら全収入をバンクする。選択解除・切替でも各研究の `researchProgressCenti` を保持し、返金・他研究への移し替えはしない。同じ研究を繰り返し選択しても二重充填しない。完了済み/前提不足は拒否、ポイント不足は拒否しない。G2のI/IIは直列前提なので、Iの中断/再開とI完了後のII選択が通常の切替操作となる。pauseで収入/充填停止、resetで進捗と選択を初期化。首都破壊後も基本収入と研究は継続する。

全陣営に基本研究収入2Centi/tick（0.2ポイント/秒）を付与し、稼働所有拠点ごと10Centi/tick（1ポイント/秒）を加える。選択命令時にバンクだけで完了した効果は次の交戦から有効。当tickの収入充填で完了した効果は次tickの交戦から有効。必要量以外の待機時間を設けない。

生産は最初のn→n+1 stepからremainingTicksを減らす。remaining=1のjobは次step開始前なら取消・返金できるが、完了step後はjobが存在せず取消を拒否する。生産待ちの開始だけは前job完了の次stepから減算する。

収入は制圧・破壊を反映した所有状態から毎tick加算し、tick開始時に存在し交戦後も生存する自軍部隊の維持費を引く。補給はmax(0,収入後残高−維持費)で0未満にならない。資源不足によるHP減少・無料生産はない。待機生産の維持費は0。

## 7. 交戦・制圧・チケット

攻撃は移動を止めず自動実行。移動後の同一snapshotから、各生存部隊がその陣営のvisible内かつ射程内の敵部隊を優先し、いなければ敵のHP>0の拠点/首都を選ぶ。同種は距離二乗→IDの辞書順。中立・味方・破壊済み拠点は射撃しない。

ダメージを一括集計し同時適用する。死亡予定の部隊も同snapshotで撃ち返す。部隊HP<=0を除去し、各死亡について一度だけチケット8を引く。首都HP0は元所有者の破壊状態を維持して視界/生産/首都収入を止め、最初の破壊時だけチケット100を引く。首都は奪取しない。所有拠点HP0は中立・HP0へ戻し、制圧進捗を初期化する。

中立拠点の半径1に交戦後の生存部隊がいる陣営を列挙する。ちょうど1陣営なら同じcandidateの進捗を+1、別candidateなら1から開始。0陣営または複数陣営ならcandidate=null/進捗0。同時に30tickを満たした拠点を所有化しHP100にする。所有済み拠点には進捗を積まず、敵はまずHPを0にする。HP0へ戻ったtickから占有を開始できる。

拠点重みは稼働所有outpostごと1、首都0。10tickごとに、各陣営のticketsCentiから `max(0, min(6, 他2陣営の重み合計 - 2 * 自軍重み)) * 10` を引く。旧仕様の平均差×0.2/秒を3陣営の整数式へ置換したもの。部隊・首都損失も含め0でクランプ。G2は3陣営を減算母集団のまま維持し、チケット0でも勝敗処理を行わない。G3では脱落陣営の除外を別途決定する。

## 8. 1tickの実行順

running以外は同一stateを返す。tick=n→n+1の順序:

1. tickを進める。
2. G1方式で部隊移動を更新。
3. 移動後snapshotで攻撃用の視界と攻撃候補を算出。
4. 全ダメージ同時適用→死亡/拠点破壊と一度限りの損失チケット→首都破壊の予約取消。
5. 生存部隊から中立制圧を更新。
6. 基本研究収入・拠点収入と維持費を適用し、選択研究へ充填して完了を判定。
7. 生産activeを更新し、完了部隊を生成。
8. 10tick境界なら拠点差チケット減算。
9. 最終視界・探索履歴・拠点観測情報を更新し、状態を返す。

当tickの所得で完了した研究効果は次tickから有効。同tick生産した部隊は攻撃しない。同時死亡・同時制圧・資源不足の順序を配列の走査順に依存させない。tick中にUIコールバックを呼ばない。

## 9. UIと検査シナリオ

mockの `s05_match_hud.html`、`s05a_research.html`、`s05b_base_popup.html`、`s05c_squad_popup.html`、`s05d_base_panel.html` を配置・情報階層の参照にする。mockの疑似処理をコピーしない。

上部に3陣営の公開チケット/停止操作、下部に自軍補給/研究/収支・部隊・生産/研究入口。拠点ポップは所有/HP/進捗/生産可否。研究は画面を覆ってもtick・チケット・進行中表示を保つ。閉じる・取消・無効理由を44px操作領域で用意する。900×420の盤面を常時巨大パネルで狭めず、生産/研究は排他的に開く。

scenarioIdは通常`standard`と検査専用`g2-capture`、`g2-combat`、`g2-economy`。検査設定に明示表示し、通常設定の初期資源を黙って変更しない。fixtureは決定的な配置・初期資源だけを変え、tick/command/交戦/視界/コストは通常と同じ関数を使う。初期値はテスト行列のfixture表で固定する。

G2の開始前に、ユーザー検査票へseed/scenario選択方法、操作順、期待tick、通常との差、全情報診断、未検証端末を記載する。ユーザー合格を親/子エージェントが代行しない。

1. G1の明示合格とmainへのマージを確認する。
2. 合格commitと本案の観測commitを比較し、状態/配置/移動/入力変更を本案へ反映する。
3. 本案の暫定値をDECISIONS/SCOPEへ採用記録し、G2専用branchを作る。
