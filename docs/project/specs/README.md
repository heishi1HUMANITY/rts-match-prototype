# 現行機能仕様の入口

このディレクトリはゲームの現行機能仕様をまとめた独立した参照資料。初回整理の実装基準はコードの `a6a9f16`。2026-10-16の採用方針を各仕様の「採用仕様（未実装）」へ反映し、「現行実装」と分けて記載する。採用仕様はこれから反映する機能の条件、現行実装は現在のコードの動作であり、採否確定だけで実装・プレイ検証済みとは扱わない。開発手順・進捗管理・承認手続きは扱わず、この入口と各仕様だけで機能を読み進められる。

AIは次の順で必要な部分だけ読む。

1. 下の機能名から仕様を選び、採用仕様と現行実装の差を確認する。
2. 相互作用を確認するときは各仕様末尾の関連仕様を読む。
3. 詳細確認には [registry.json](registry.json) の `sources` から実装へ進む。テストは各仕様末尾を参照する。
4. 実装済みの数値は [DEFAULT_RULES](../../../src/simulation/rules.ts) とその入力元 [config.ts](../../../src/simulation/config.ts) を読む。試合中は `MatchState.rules` が適用値で、保存済みマスタや標準値とは異なる場合がある。未実装の採用条件に対する具体値は算出前であり、旧標準値が新条件を満たすとは扱わない。

## 今回反映した採用仕様

- 試合の判断基準は[試合進行・決着](MATCH.md)。20分で完結するミニCivとして、地形と隣人から研究・拡張・戦い方を選ぶ。
- 定額研究/補給、研究段1〜3の非排他・前段OR、段4だけの専攻排他、完了数による必要量増加、逆転不変条件、陣営傾向は[補給・生産・研究](ECONOMY.md)。具体値は算出待ち。
- 定義データ化、現行マップ2.5倍の100×100試行、A開始地点のseed選択、固定構造の複数マップ、開始地点別勝率20〜50%は[地形・渡河設備](WORLD.md)。最初の試行は現行ルールで行う。
- 地形からの道筋選択、公開情報による中盤対応、判断品質/速度による難度は[対戦NPC・現地勢力](NPC.md)。人間の勝率目安は自動対戦から推定しない。
- 航空対空・地点砲撃・非火力専攻・戦闘予測の詳細は後続で定義する。各仕様で未確定/未提供の範囲を示し、相談中の候補値を確定値にしない。

採否の根拠は[決定記録](../DECISIONS.md)と[Issue #79](https://github.com/heishi1HUMANITY/rts-match-prototype/issues/79)。実装順やプレイ確認のまとまりは機能仕様ではなく、開発運用とIssueで管理する。

## 記載範囲

- 採用済みの機能条件と現在の動作、前提条件、例外、設定項目、機能間の関係を記載する。未決定の具体値は未確定と明示し、未採用の将来案や過去の設計経緯は仕様として採らない。
- 提供していない機能と標準で無効の機能は本文で区別する。動作の記述はプレイ品質の評価を意味しない。
- コードと採用仕様に差があれば未反映として明示する。実装時は該当範囲の現行実装の節も更新し、古い動作を残したまま実装済み表示にしない。

## リンクと更新対象の構造

`registry.json` は機能名（`name`）、固定の英語キー（`id`）、文書パス、実装パス、確認済み実装のSHA-256を持つ。英語キーは `MATCH` や `ECONOMY` のような意味のある名前とし、検査コマンドで使用する。機能の連番・総数・順序は管理しない。追加・削除時は対象の項目と索引だけを変更し、他機能の名前を振り直さない。

行番号・見出しの自動生成アンカーに依存せず、ファイルへの相対リンクで参照する。機能名の表現を変えてもファイル名は原則固定する。統合・分割時は旧パスに案内を残し、対応表と全参照を更新する。

実装済み数値の正本は実装マスタとし、仕様本文へ可変の数値表を重複転記しない。本文には設定キーと意味、採用不変条件を記す。未実装のキーや値を実在する設定と扱わない。関連仕様は相互リンクで参照し、同じルールを複数文書へ複製しない。

## 資料の整合性確認（任意実行）

資料専用の検査コマンドを用意している。通常の開発チェックからは独立しており、資料を確認・更新するときに単独で使用できる。

```sh
npm run specs:check
# 表示された担当仕様と関連仕様を確認・修正した後、確認した英語キーだけ指定
npm run specs:review -- MATCH ECONOMY
npm run specs:check
```

`specs:check` は実装との差分から見直し候補の機能名と英語キーを示す。本文と関連仕様を確認し、必要な修正後に `specs:review` で参照した実装のハッシュを記録できる。文言変更が不要な場合も確認後に記録する。ハッシュは仕様の自動生成・正しさの証明ではなく、参照した実装の記録。本文の意味の更新漏れまでは自動判定できない。

検査対象は、仕様内の相対リンク、明示アンカー、対応表の参照先、実装ハッシュ、未登録の本番srcファイル、機能名・英語キーの重複。外部URLの死活と他の資料全体のリンクは検査範囲外。改行はLF/CRLFを正規化して比較する。
