# Issue番号から作業するエージェントの手順

この文書は会話履歴を持たないエージェント向けの入口。ユーザーが `#30`、`issue 30`、`30を進めて` のように番号を渡したら、対象Issueの作業指示として扱い、調査だけで終わらず実装・検証・検査可能なPRまで進める。ユーザーに実装プロンプトや技術設計を再作成させない。

## 最初の照合

1. `git status --short`、`git remote -v`、現在ブランチを確認する。対象は `heishi1HUMANITY/rts-match-prototype`。このPCの実体は `D:/git/rts-match-prototype`、`D:/git/rts` は継承元。別PCではパスを固定せずremoteで照合する。ユーザーの未コミット変更を上書きしない。
2. AGENTS、README、SCOPE、ARCHITECTURE、DECISIONS、WORKFLOWを読む。対象Issueの本文だけでなくコメント、ラベル、関連PRのhead・CI・マージ状態を取得する。例: `gh issue view 30 --comments`、`gh pr list --state all --search "30"`。検索結果は本文と関連Issueを照合し、番号の一致だけで選ばない。
3. [タスク別実装ガイド](ISSUE_IMPLEMENTATION_GUIDE.md)の対象見出し、[網羅表](GAMEPLAY_COVERAGE.md)、リンクされた現行設計・旧仕様の該当章を読む。旧資料の「実装済み」は現在の実装根拠にならない。
4. [引き継ぎ時点の状態](AGENT_HANDOFF.md)は探索の手掛かりとして使う。現在のGitHubと実コードが正で、過去のport・プロセス・schema・テスト件数を現在の事実として流用しない。

IssueとPRは別の番号体系。Issueが見つからず同番号のPRだけ存在する場合は、勝手に別作業を始めず対象を短く確認する。接続や認証が使えなければローカル資料から独立して進められる部分を進め、未確認事項を明記する。

## 状態別の動き

| 現在の状態      | 番号だけを受け取ったときの行動                                                                            |
| --------------- | --------------------------------------------------------------------------------------------------------- |
| ready           | 本文の依存・gate・CPを確認し、実装計画をIssueコメントへ記録して着手する。CP0完了前は次Fの本実装へ進まない |
| implementing    | 既存ブランチ・PR・未コミット変更・引き継ぎを調べ、残作業を継続する。重複PRを作らない                      |
| review          | 別会話・読み取り専用モデルと受入条件ごとのOK/NG・根拠行を照合する。最大2修正巡でNGが残ればこの状態で停止  |
| closed / merged | 完了内容を照合し、再実装しない。修正が明示されていれば元の版に関連付けた修正作業を行う                    |

必須依存は「未実装の型・APIやルールがないと対象機能が成立しないもの」。推奨順とは分けて本文へ書く。依頼範囲内のPRはWORKFLOWのDoDでマージし、機能ごとのユーザー合格は求めない。独立できる設計・基盤部分は進め、必須依存が必要になった時点で不足を具体的に示す。依存を模擬しただけで完了扱いしない。

例: #30は#14の追跡仕様を参照するが、マスタ編集・検証・保存の設計は独立して進められる。#14が未マージなら、その事実を記録し、実装基点に存在するルールを対象にする。#14のコードを混ぜた場合は関連付けと統合後の再検証が必要。

## 実装を最後まで進める

1. 利用者に見える結果、受入条件、必須/推奨依存、変更する状態・command・表示・AI・診断、既知の未決定事項を整理する。対象Issueコメントへ短い計画を記録する。大きい機能は `docs/project/preparation/Fxx_DESIGN.md` に具体契約を保存し、Issueからリンクする。
2. 採用済みのふるまいを維持する。研究は充填式・未指定バンク・進捗保持・基本収入あり。移動はドラッグ、複数選択・集団指示あり。人間とB/Cは同じ費用・視界・command。旧30分、旧研究待ち時間、文明・オンラインを黙って戻さない。
3. 通常の設計判断や仮の調整数値はエージェントが決め、単位・理由・暫定性をDECISIONSとマスタへ残す。ユーザーに型、ファイル、アルゴリズムを選ばせない。ゲームの目標・採用機能・承認済みルールを大きく変える場合だけ、選択肢と遊びの差を短く示して確認する。その間も独立作業は進める。
4. mainの最新状態か既存PRの続きから専用ブランチで進める。共有型/APIを先に決め、simulation、runtime/AI、UI/render、検証を必要に応じて分担する。委任では編集可能ファイルと完了条件を明記し、親が統合・外部記録を担当する。既存の[実装指示テンプレート](templates/IMPLEMENTATION.md)を親が埋める。
5. pure simulationのJSON状態と固定tickにルールを置く。変更に応じて共通command検証、viewの情報制限、AI、画面の理由表示、reset/終了、診断replayを一緒に更新する。数値は#30導入後、その試合に適用中の不変マスタを参照する。
6. その機能が通常対戦で使えるまで接続する。メニューだけ、内部APIだけ、固定fixtureだけで完了にしない。無効理由と短い操作案内、短時間fixtureを用意し、通常設定と区別する。
7. 意味のある境界テストと、SCENARIOSの項目からPlaywright e2eを追加する。`npm run check`、`npm run references:check`、Windows/Linux CIと該当e2eを成功させる。別会話・読み取り専用モデルで受入条件を照合し、固定headのOK/NGと根拠行をPR本文へ貼る。最大2修正巡でNGが残ればflow:reviewのまま停止する。UIは実ブラウザPC/900×420/タッチ対応を確認し、実機とエミュレーション、未検証を区別する。
8. コミットして作業ツリーをcleanにし、そのSHAからbuildする。`dist/build-info.json`のSHA/dirty/schema/rulesを照合する。HTTP応答だけでは画面検査済みにしない。PRを作成/更新して対象Issueに関連付け、完全SHA・CI・検査票・URL/起動方法・未検査を記録する。利用環境にPR添付ツールがあれば添付する。
9. DoDを満たした依頼範囲のPRをマージし、flow:mergedと#12のマージ済み列を更新する。gate:playにはstatus:unverifiedを付けてCP票へ自動収載する。ユーザーに機能ごとの合格依頼はしない。CPが締まったら[CP票](inspection/CP_TEMPLATE.md)で通常1試合・確認3点・既知未検証を提示する。

## CP結果と再開

ユーザーの「CP1 OK / NG(#番号)」はMilestone所属の検査結果Issueコメントへ記録する。Milestone自体にはコメント欄がないためこのIssueを使う。OKの対象だけ#12のプレイ検証済み列へ記録し、status:unverifiedを外す。NGは元Issueに紐づく修正Issue/PRで対応し、同じDoDでマージ後CP検査へ戻す。CP0完了が次のF実装の前提。kind:decisionはユーザーの明示採否を待ち、実装Issueと分ける。

文書/CIのみの保守はgate:autoとし、非該当シナリオの理由をPRへ記録する。依頼外のゲームコードを混ぜない。

コンテキスト/利用上限で止まる前にIssueまたは引き継ぎコメントへ、ブランチ、基点/最新SHA、変更ファイル、未コミット有無、済/未チェック、残作業、既知の問題、次の一手を保存する。ローカルの `.local-qa` やチャット、消える子エージェントの記憶だけに残さない。未完成の差分を勝手に破棄・巻き戻ししない。
