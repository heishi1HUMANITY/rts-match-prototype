# 世界観レビューの協業フロー

> この文書は協業手順であり、世界観の正史ではない。既存の `01`〜`10` と README は読み取り専用とする。前回の逐次追記台帳 `12_修正案協議台帳.md` は協議記録として残し、次回の作業ファイルにはしない。

## 役割と対等性

- **Codexは進行役・統合担当。** 対象範囲、証拠、論点の重複、作業状態を管理し、統合案を作る。Geminiより上位の判断者ではない。
- **Geminiは独立した共同レビュアー。** Codexの結論を追認する役ではなく、独立に問題を見つけ、統合案へ反証・修正を提案する。
- **判断基準は対称。** どちらの指摘も、本文の根拠・具体的な破綻例・修正の副作用で評価する。合意は多数決や進行役の裁定ではなく、二者が論点ごとに明示する。

## 作業領域と衝突防止

1. 1回のレビューごとに `docs/story/review-runs/<run-id>/` を作る。例: `docs/story/review-runs/2026-10-08-world-rules/`。
2. `00_scope-and-manifest.md` に対象ファイル、対象版、SHA-256、レビュー目的、除外範囲を記す。原資料を改稿したら旧Runは閉じ、新しいRunを作る。
3. CodexとGeminiは別ファイルに書く。共有ファイルを同時編集しない。

```text
review-runs/<run-id>/
  00_scope-and-manifest.md       # 対象と基準版
  01_codex-independent.md        # Geminiの独立レビュー完了前は見せない
  02_gemini-independent.md       # Geminiの初回レビュー。原資料だけを読む
  03_issue-register.md           # 論点ID、根拠、状態。Codexが更新
  04_codex-synthesis-r01.md      # 初回統合案
  05_gemini-cross-review-r01.md  # 統合案への反証・同意
  06_codex-synthesis-r02.md      # 合意を反映した次案
  gemini-prompt-*.md             # そのターンの資料抜粋と依頼。Codexが準備
  gemini-turn-*.json             # agy応答の生JSON
  gemini-session.json            # conversation_idと成功状態
  ...
  final-proposal.md              # 二者合意後の修正案。正史本文ではない
  decision-log.md                # 合意・保留・判断理由の短い記録
```

Geminiには原則 `01_codex-independent.md` を見せる前に独立レビューを出してもらう。初回提案が揃った後は、互いの案を見て反証する。Geminiの出力は別ファイルに保存し、Codexが内容を検証して論点台帳へ統合する。どちらも相手のファイルを編集しない。

## 進め方

1. **範囲を固定する。** 「世界法則」「短編06の因果」など、1 Runの問いを絞る。現行の01〜10、README、必要な補助資料をマニフェストに記録する。
2. **独立レビューを行う。** CodexとGeminiが同じ資料を独立に読み、各自のレビューを別ファイルに作る。指摘は問題の重大度、根拠となる節、読者が遭遇する具体例、最小修正、修正の副作用を含める。
3. **論点を正規化する。** Codexが重複をまとめてIDを付ける。指摘の統合は記録の整理であり、異論を消すことではない。Geminiは統合された論点一覧に抜けや誤読がないかを確認する。
4. **論点単位で議論する。** 各側は相手の主張に対し、根拠・反例・副作用を返す。新しい事実を主張する場合は対象ファイル・節を示す。別論点を一度に混ぜず、修正案が新たな能力・組織・技術を増やす場合は、その追加コストも評価する。
5. **統合案を作る。** Codexが各論点を「合意」「一部合意」「保留」「却下」に分類し、合意済みのものだけを修正案へ反映する。Geminiが統合案を敵対的に読み、修正後に残る矛盾、都合よく追加された能力、説明ノイズを探す。
6. **必要な限り反復する。** 新しい反例が出た論点だけ再検討する。前ラウンドの文面を繰り返すだけなら、その旨を明記して打ち切り候補にする。3回続けて同じ理由で合意できない論点は、合意と偽らず選択肢・利点・代償を並べてユーザーに判断を求める。
7. **終結を確認する。** 二者が重要論点に明示的に合意し、最終案を独立に読んでも重大な矛盾・ご都合主義・説明ノイズを見つけないと確認してから完了とする。意見が残るなら未解決のまま残す。

## 論点カードの形式

```markdown
### W-001 — 盤面勝敗と少女の介入
- 重大度: Critical / High / Medium / Low
- 根拠: `02_少女と夢境.md` §2.1、`06_短編_境界線のクレヨン.md` §3
- 問題の因果: 誰が何をしたため、どのルールが破れるか
- 具体的な破綻例: 読者が本文から推論できる矛盾・不自然さ
- 最小修正案:
- 副作用・新たに増える設定:
- Codexの立場: agree / disagree / partial / evidence-needed
- Geminiの立場: agree / disagree / partial / evidence-needed
- 状態: open / agreed / deferred / rejected
- 合意理由または保留理由:
```

「面白くない」「説明不足」のような抽象評だけでは論点を閉じない。具体的な読解・因果上の問題に翻訳できない場合は、好みや演出上の選択として区別する。

## Agyを継続セッションで使う

`agy -p` は一回の応答を得る実行だが、応答JSONの `conversation_id` を保存すれば同じGemini会話へ次の依頼を渡せる。初回は `--conversation` を省き、二回目以降はIDを指定する。`--continue` は別の直近会話を誤って引き継ぐ恐れがあるため使わない。

このリポジトリには、Runの雛形作成とセッション継続を補助する `scripts/story-review/New-StoryReviewRun.ps1` と `scripts/story-review/Invoke-AgyReviewTurn.ps1` を置く。Run作成スクリプトにはレビュー対象ファイルを渡し、SHA-256付きマニフェストを生成する。ターンスクリプトにはRunディレクトリと、そのターンの依頼・抜粋を含むプロンプトファイルを渡す。初回は会話IDなし、二回目以降はRun内の `gemini-session.json` に保存したIDで続行し、応答JSONを別ファイルに保存する。

```powershell
./scripts/story-review/New-StoryReviewRun.ps1 -Name world-logic -SourceFiles @('docs/story/01_世界構造と歴史.md','docs/story/02_少女と夢境.md')
./scripts/story-review/Invoke-AgyReviewTurn.ps1 -RunDirectory 'docs/story/review-runs/<作成されたrun-id>' -PromptPath 'docs/story/review-runs/<作成されたrun-id>/gemini-prompt-independent.md'
./scripts/story-review/Invoke-AgyReviewTurn.ps1 -RunDirectory 'docs/story/review-runs/<作成されたrun-id>' -PromptPath 'docs/story/review-runs/<作成されたrun-id>/gemini-prompt-cross-review.md'
```

レビュー用プロンプトには、対象資料の必要な抜粋を入れる。ファイル名だけを渡してCLIに作業領域を自由探索させる運用に依存しない。`gemini-session.json`が`active`になり、応答JSONに本文と`conversation_id`があることを確認してから次のターンへ進む。

```powershell
# 初回: Geminiに独立レビューを依頼する。<PROMPT>はレビュー用プロンプト本文。
agy -p $prompt --model gemini-3.8-flash-high --effort high --mode plan --sandbox --output-format json --print-timeout 10m

# 続き: 初回JSONのconversation_idを保存し、同じ会話へ統合案の反証を依頼する。
agy -p $prompt --conversation $conversationId --model gemini-3.8-flash-high --effort high --mode plan --sandbox --output-format json --print-timeout 10m
```

プロンプトは会話履歴に頼らず、その回の対象、資料、論点ID、編集禁止範囲、出力先を明記する。複雑な依頼はUTF-8のプロンプトファイルから読み込み、応答JSON全体をRunの記録へ保存する。`conversation_id` と本文が得られたことを確認し、終了コードだけで成功と判断しない。権限回避オプションは使わない。Geminiには原資料の編集を頼まず、`--mode plan --sandbox` を基本にする。

**Headless実行の失敗判定:** JSONの`status`が`SUCCESS`でも、`response`が空、`denied_actions`が空でない、またはCLIが「tool permissionが必要」と報告した場合は、レビュー未実施として扱う。`--dangerously-skip-permissions`で再試行しない。通常の承認が可能な対話セッションを使うか、Geminiのレビューが実行できなかったと記録してCodex側の確認だけを続ける。今回のフロー案のGemini確認ではコマンド権限が拒否され、応答本文を得られなかったため、Geminiレビュー済みとは扱っていない。

## 受け入れ基準

- 事実主張には参照箇所がある。
- 矛盾は本文の具体例と因果で説明されている。
- 修正案が中心ルールと整合し、後付け能力や例外を増やしすぎない。
- 物語上必要な情報と、制作・運営メタ情報が分けられている。
- 合意・保留・不採用が区別され、未合意を合意扱いしない。
- 最終成果物は、完全な修正文案または差分案、論点ごとの判断、未解決事項、変更対象一覧を含む。
